# ASK 文档工程规范

## 1. 文档目标

本目录是 ASK 产品和技术设计的事实来源。设计文档必须能够指导需求评审、数据建模、接口实现、前端交互、测试验收和部署运维；聊天记录和口头约定不作为最终设计依据。

## 2. 文档语言与命名

- 产品、需求、业务规则、架构决策和验收文档优先使用简体中文。
- 代码标识符、表名、字段名、API 路径、协议名保留英文。
- 文件名使用两位序号加 kebab-case，例如 07-field-review.md。
- 同一概念使用唯一中文名称和唯一英文标识；术语变更必须同步更新术语表与引用文档。
- 日期使用 YYYY-MM-DD；时间戳使用带时区的 RFC 3339。
- 示例中的 ID、密钥、用户数据均为虚构数据。

## 3. 文档状态

每份设计文档开头必须标记状态：
- Draft：正在设计，不能直接作为实现承诺。
- In Review：待评审，存在待决事项。
- Accepted：已评审，可作为实现依据。
- Superseded：被新版本取代，保留历史链接，不再作为当前依据。

当前阶段所有新设计默认是 Draft。未完成评审的 SQL 不得标记为生产可用。

## 4. 文档目录

- requirements/：产品能力、用户旅程、功能拆解、需求 ID 和验收条件。
- architecture/：领域、数据、API、AI 流水线、前端、部署、安全、测试和 ADR。
- operations/：部署、监控、备份、故障恢复手册，进入实施阶段后建立。
- decisions/：如 ADR 数量增加，可从 architecture 中独立拆出。

## 5. 需求追踪

每条需求使用稳定 ID：
- CAP：产品能力。
- FR：功能需求。
- BR：业务规则。
- NFR：非功能需求。
- API：接口契约。
- DATA：数据约束。
- TEST：验收用例。

需求链路应当是：
能力 CAP → 功能 FR → 业务规则 BR / 数据约束 DATA → API → 测试 TEST。

需求 ID 不因标题或页面名称修改而变化。废弃需求应标注 Superseded 和替代 ID，不得直接删除。

## 6. 设计变更流程

涉及下列内容的变更，必须检查关联文档：
- 数据字段、外键、状态值：数据字典、SQL、API DTO、迁移说明、测试。
- 分析输出结构：Artifact Schema、提示词、验证器、前端组件、回归样本。
- 用户操作或页面流程：功能拆解、用户旅程、API、权限和验收。
- 模型或提示词：分析流水线、成本预算、质量评估和可复现性。
- 权限、保留期或文件存储：安全设计、数据生命周期和运维手册。

PR 必须说明变更动机、受影响文档、兼容性、迁移策略、验证状态和未决事项。

## 7. 设计文档模板

每份详细设计至少包含：
1. 目的与范围。
2. 术语与依赖。
3. 方案与数据/交互流程。
4. 字段或接口定义。
5. 状态、权限和业务规则。
6. 异常与边界情况。
7. 可观测性与安全要求。
8. 验收标准。
9. 未决事项和决策记录。

## 8. 当前文档状态

已有的 00–05 文档属于第一轮架构草案。新建的详细设计文档用于补齐产品功能、字段定义、数据完整性、接口、交互、AI 质量和运维要求。所有设计完成后统一评审，不因文件数量增加而自动视为已定稿。
