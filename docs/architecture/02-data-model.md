# PostgreSQL Data Model

## 1. Storage strategy

PostgreSQL is the transactional source of truth for projects, works, source metadata, chapters, analysis state, story entities, relations, events, plotlines, outlines, claims, and evidence anchors.

Object storage holds original uploads and may hold large intermediate exports. The first implementation stores normalized chapter text in PostgreSQL so the reader, evidence viewer, and analysis worker can share stable chapter IDs and offsets. If corpus scale later makes this expensive, chapter text can move behind a content repository interface without changing domain IDs.

Use JSONB for evolving model payloads, source metadata, attributes, input manifests, and task progress. Do not use JSONB instead of relational tables for entities, events, relations, plotline nodes, outline hierarchy, or evidence anchors.

## 2. Table groups

### Identity and workspace

- app_users
- projects
- project_members
- works
- project_works

A project owns access control. A work represents the intellectual work. project_works links them and supports primary, reference, and inspiration roles.

### Source and segmentation

- source_documents
- source_versions
- split_versions
- source_chapters

A source version is produced by a parser/normalizer. A split version records a chapter segmentation over that source version. Source chapters belong to exactly one split version.

### AI execution and outputs

- analysis_runs
- analysis_run_steps
- artifacts
- analysis_claims
- evidence_anchors

Runs are execution records; artifacts are durable output revisions. Claims are reviewable statements. Evidence anchors locate supporting source spans.

### Story structure

- story_entities
- entity_aliases
- story_relations
- story_events
- event_relations
- plotlines
- plotline_nodes
- outline_sets
- outline_nodes

Use explicit edge tables for entity and event relationships. A plotline node may point to a chapter, event, or both. Outline nodes form a tree within one outline set.

## 3. Keys and naming

- Primary keys are UUIDs generated by PostgreSQL.
- Foreign keys are explicit and indexed where they support joins.
- All timestamps are timestamptz and written in UTC.
- User-facing order is represented by integer/bigint position fields, not inferred from UUID order.
- Use soft archival statuses for story entities and artifacts where history must remain visible. Do not hard-delete source versions that are referenced by analysis.
- Avoid database enums in the first migration; CHECK constraints are easier to evolve during early product development.

## 4. Versioning rules

### Source versions

A source version is immutable and identified by:
- source document;
- monotonically increasing version number;
- content SHA-256;
- parser and normalization versions;
- normalization configuration.

### Split versions

A split version belongs to one source version and contains the segmentation configuration and confirmation state. Editing a boundary creates a new split version with a new set of source chapters. Do not update chapter offsets in place after evidence has been generated.

### Artifacts

An artifact has:
- stable artifact_key within a work, such as book-overview or chapter-outline:<chapter-id>;
- artifact_type;
- monotonically increasing revision within that key;
- optional source/split version;
- payload JSONB and optional rendered Markdown;
- status and provenance to its producing run;
- optional supersedes relationship.

The application must determine the next revision transactionally. The unique constraint on work, artifact key, and revision prevents concurrent duplicate revisions.

### Evidence offsets

- start_char is inclusive; end_char is exclusive.
- Offsets are measured against source_chapters.content_text after canonical Unicode normalization.
- quote_text is stored for display and verification.
- quote_sha256 is computed over the exact UTF-8 encoding of quote_text.
- If normalization or chapter text changes, create new chapter identities rather than mutating the old text.
- Evidence verification must compare the quote with the actual span before presenting a claim as source-supported.

## 5. JSONB contract

JSONB is appropriate for:
- work metadata and entity attributes;
- parser/split configuration;
- analysis input manifest and progress;
- artifact-specific fields that vary by artifact type;
- event/relation attributes.

JSONB is not appropriate for:
- the only representation of characters or plotlines;
- lists that need independent filtering, ordering, joins, or referential integrity;
- evidence spans;
- outline parent/child relationships;
- task status or idempotency keys.

Version the schema of structured model payloads using a field such as schema_version. Validate model output against a server-owned schema before persistence.

## 6. Index strategy

Initial indexes should cover:
- project membership by project and user;
- project-work joins in both directions;
- source document lookup by work and checksum;
- source versions by document and version number;
- split versions by source version and version number;
- chapters by split version and chapter number;
- analysis runs by project/work/status/created time;
- run steps by run and sequence;
- artifacts by work/key/revision and run;
- entities by work/type/name and aliases by normalized alias;
- events by work/narrative order and chapter;
- relations by source and target entity;
- plotline nodes by plotline/position and event;
- outline nodes by set/parent/position;
- evidence anchors by claim and chapter/span.

Add full-text or vector indexes only after retrieval requirements and query patterns are measured.

## 7. Deletion and retention

- Deleting a project must not cascade-delete a work that is also linked to another project.
- Deleting or replacing an upload must not remove historical source versions referenced by completed runs.
- Source retention and user-initiated permanent deletion need an explicit service-level workflow that removes object storage data and dependent records safely.
- Cascades are suitable for purely owned child rows such as run steps, aliases, or nodes; they are not suitable for shared works or immutable source history.


## 8. Cross-object integrity enforced by the database

The initial migration uses composite foreign keys where they protect important semantic boundaries:

- Analysis runs, artifacts, and outline sets cannot pair a split version with a different source version.
- Entity relations cannot connect entities from different works.
- Event relations cannot connect events from different works.
- An outline node's parent must belong to the same outline set, so one outline tree cannot accidentally contain a node from another version.
- Entity merge targets must belong to the same work.

Some cross-object checks still belong in the application service because the relevant ownership path crosses multiple tables, such as verifying that an evidence anchor's chapter belongs to the same work and split version as its artifact. The service must validate these conditions in the same transaction that persists the mutation.

## 9. Migration execution

The SQL files intentionally do not contain explicit BEGIN/COMMIT statements. The migration runner should own transaction boundaries, avoiding nested or prematurely committed transactions. The initial schema targets PostgreSQL 14 or newer.

Before the migration is considered complete, execute both up and down migrations against a clean PostgreSQL instance and run integration checks for foreign keys, check constraints, unique constraints, and rollback order.
