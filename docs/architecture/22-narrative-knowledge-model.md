# 叙事知识模型与小说拆解流水线

状态：Draft · 详细设计

## 1. 核心模型：文本证据 → 叙事知识 → 解释

ASK 需要分开存储三个层次：

1. **文本证据层**：规范化正文、章节/场景范围、原文提及、引用区间和 hash。
2. **故事模型层**：人物、事件、状态变化、时间关系、因果关系、信息流、故事线和结构节点。
3. **解释层**：主题、人物弧、伏笔、叙事策略、作者意图候选、结构评价和替代解释。

上层结论可以引用下层对象，但不能覆盖下层证据。解释层永远允许存在争议。

## 2. 四种顺序/关系必须分开

| 维度 | 含义 | 示例 |
|---|---|---|
| text/narrative order | 文本何时呈现一个事件 | 第 1 章先展示尸体，第 20 章才回忆案发 |
| story-world time | 事件在故事世界何时发生 | 案发在故事第 5 年 |
| causal/logical relation | 一个事件是否导致、促成、阻止另一个事件 | 伪造诏书导致将军调兵 |
| information/reveal order | 读者/角色何时知道某件事 | 读者第 1 章怀疑，主角第 8 章确认 |

一个事件可以有多个叙述提及；同一故事事件可以在不同版本、不同章节中被重复讲述。事件的“发生”与它的“被提及/被讲述”不能使用同一对象表达。

## 3. 主要实体与关系

### 3.1 文本位置
- SourceVersion：不可变规范化文本版本。
- SplitVersion：对一个 SourceVersion 的章节划分版本。
- Chapter：特定 SplitVersion 内的章节。
- SceneMention：可选的场景边界候选，绑定章节和原文范围。
- EvidenceAnchor：引用区间、引用文本、文本 hash、验证状态。

### 3.2 人物与实体
- CanonicalEntity：作品范围内的人物、地点、组织、物件、概念。
- EntityMention：某一 source/split/chapter 中出现的称呼及范围。
- AliasCandidate：候选别名及其依据。
- EntityStateObservation：人物在特定时间/叙述位置的目标、知识、信念、关系、资源、地位或风险变化。
- EntityRelation：有类型、有方向、可带有效时间/叙事范围和证据的关系。

实体消歧首先建立 mention，再与 canonical entity 关联。相似名称、共现或 embedding 相似度只用于产生候选，不足以自动合并。

### 3.3 事件
事件至少包含：
- event_key、summary、participants。
- action/decision/goal（有证据时）。
- preconditions、trigger、outcomes/consequences。
- story_time_value 或 story_time_label。
- epistemic_status、review_status。
- source/run provenance。

EventMention 记录某个事件在特定文本位置的讲述：
- source_version_id、split_version_id、chapter_id。
- local_order、narrative_order。
- mention span、evidence anchor。
- 当前叙述视角/信息状态（可选）。
- story_time_label 和 time precision。

EventRelation 需区分关系类型，至少支持 temporal_precedes、causes、enables、prevents、motivates、reveals、contradicts、foreshadows、pays_off、echoes。关系本身有独立证据、推断状态和审核状态。

### 3.4 故事线与结构
- Plotline：某个持续冲突/目标/问题的叙事轨迹。
- PlotlineNode：该故事线中的事件、章节或转折节点。
- OutlineSet/OutlineNode：可变层级的结构树。
- ThreadLedgerItem：悬而未决的问题、秘密、承诺、伏笔、任务、债务或预言，以及其状态变化。

同一个事件可属于多条故事线；故事线不是把事件简单分组，而是带有目标、冲突、进展和收束语义的选择性路径。

## 4. 每条结论都要有认知状态与审核状态

认知状态：
- explicit：原文明确表达。
- inferred：基于多处证据推断。
- speculative：存在多种合理解释或证据不足。

审核状态：
- unreviewed、accepted、rejected、edited。

这两个维度正交。例如，用户可以接受一条“推断”，但它仍然不是“原文明示”。被拒绝的结论也应保留历史，避免同一错误在重跑后无休止出现。

证据状态单独管理：candidate / verified / invalid / unavailable。不能因为用户接受了结论，就把无效引用变成 verified。

## 5. 拆解流水线

### Stage 0：输入固定
保存 source version、split version、解析配置、分析范围、模型路由、prompt/schema 版本。输出 run input manifest。

### Stage 1：结构预处理
- 识别章节标题、回目、卷标题和目录。
- 保留段落、对白、引用、注释和文本范围。
- 检查空章节、重复章节、乱码、异常重复文本。
- 场景边界先作为候选；章节不能直接等同于场景。

### Stage 2：局部文本分析
对每个章节做有界上下文分析，提取：
- 事件候选和事件参与者。
- 人物/实体 mention。
- 状态变化、目标、选择、冲突和后果。
- 新信息、隐藏信息、误认/重新解释。
- 叙述视角、故事时间线索和叙述顺序。
- 章节功能与未解决问题。
- 引用候选和原文范围。

每个候选引用必须包含原文可定位的 quote/span；模型返回的 offset 只能作为候选，服务端按规范化文本验证。

### Stage 3：实体解析
- 规范化称呼、别名候选。
- 结合前后文、角色关系、称谓、时间和知识状态匹配实体。
- 生成冲突证据，例如年龄/身份/地点/关系矛盾。
- 高歧义情况进入人工消歧队列。
- 只有通过规则或人工审核后才确定 canonical mapping。

### Stage 4：事件解析与关系推断
- 将重复描述聚合为 canonical event 候选，同时保留各自 EventMention。
- 建立叙事顺序和故事时间两个视图。
- 对时间关系、因果关系、动机关系和信息揭示关系分别提出候选。
- 对每条隐含因果关系给出“为什么认为 A 导致 B”的证据。
- 不因相邻、同人物或语义相似就自动建立因果边。

### Stage 5：故事线候选
从共享事件/人物关系图中提出若干路径：
- 共同目标/冲突驱动的事件链。
- 特定人物的目标和状态变化。
- 持续未解的谜团、秘密、债务、承诺或预言。
- 跨线交汇和互相改变结果的事件。

用户可合并、拆分、改名和调整线的类型；算法建议不是最终分类。

### Stage 6：宏观综合
在章节事实和事件图基础上，生成：
- 卷/部/故事弧候选。
- 主线/支线及交汇。
- 关键转折、高潮、结局、余波。
- 叙述顺序与故事时间差异。
- 伏笔/回收候选、重复母题、主题问题。
- 叙事节奏和视角分布。

全书综合必须引用已保存的事件/结论，不得仅凭逐章摘要二次幻觉。

### Stage 7：校验与审核
- Schema 校验。
- 资源/版本/章节关系校验。
- 引用文本和 hash 校验。
- 实体冲突与事件重复检测。
- 时间线和因果链矛盾检测。
- 伏笔/回收是否有证据。
- 结论覆盖率与不确定性检查。
- 用户审核及错误类型反馈。

### Stage 8：局部重算
每个产物声明依赖项。章节重跑只重算受影响的实体/事件候选和聚合；实体合并只重算受影响关系和故事线；切分版本变化使旧证据保持历史状态，不做静默迁移。

## 6. 长篇上下文策略

- 不把整本小说塞进一次请求。
- 按章节/场景做局部分析，使用滚动上下文窗口：前情摘要、当前章节、必要人物状态、相关事件、开放线索。
- 维护结构化状态，不只维护自由文本 summary。
- 全书综合使用事件索引、人物状态、故事线索引和分层摘要。
- 对每个阶段记录实际输入清单，确保可复现。
- 跨章节推断要允许检索原文证据，而非只依赖旧摘要。

## 7. 质量评价

建立人工标注的代表性语料，至少包含：
- 线性情节小说。
- 多视角/倒叙小说。
- 悬疑/推理小说。
- 群像/历史长篇。
- 章回体或超长连载。

评价维度：
- 事件 precision/recall。
- 人物 mention 归并精确率、错误合并率。
- 时间关系和因果关系精确率。
- 关键结论证据有效率。
- 故事线与伏笔判断的人类一致性。
- 用户修正次数和完成全书审核时间。

不得以单一“模型 confidence”替代人工评估。
